# 工程原则

> 六条原则适用于任何仓库与语言，是 coding 与 qa Agent 的共同约定。每条给出一个正例与一个反例，便于对照执行。

## 1. 先读后改

动手前先读懂需求、相关代码、调用点与仓库约定；事实（接口签名、配置键、命令名）必须有出处。

- 正例：修改函数签名前，先列出全部调用点与相关测试，确认影响面后再动手。
- 反例：只看了函数实现就调整参数顺序，结果三处调用点编译失败。

## 2. 清单驱动

任务超过三步就拆成可独立验证的小项，同一时间只推进一项，完成即勾掉并在 Issue 留痕。

- 正例：`- [ ] 2. 新增 docs/principles.md，六条原则各含正例与反例`，完成后立刻标记。
- 反例：一边写 README 一边改 CI 配置，两项都没验证就说「基本完成」。

## 3. 最小且一致

只改需求范围内的内容；沿用现有命名、目录、风格与依赖；不顺手重构，不引入未说明的新依赖。

- 正例：修复一处文档链接用一行改动，其余排版保持仓库现状。
- 反例：顺手把整个目录的缩进从两空格改成四空格，diff 淹没真实改动。

## 4. 验证闭环

找出仓库真实的 lint / 类型检查 / 测试 / 构建命令并运行；PR 中写出命令与结果，证据优先于自信。

- 正例：PR 写明 `markdownlint "**/*.md"` 运行通过（规则集来自 `.markdownlint.jsonc`），并附关键输出行。
- 反例：只读代码就说「应该能跑」，未执行任何检查。

## 5. 安全边界

凭证只从环境变量读取，绝不写入代码、日志、评论或提交信息；不可逆操作与合入一律留给人工。

- 正例：CI 中通过 secrets 注入令牌，脚本只引用变量名，不打印其值。
- 反例：调试时把请求头连同令牌一起打进日志，令牌随日志长期留存。

## 6. 简洁汇报

结论先行：做了什么 → 怎么验证 → 风险与待确认；用 `path:line` 指位置，不贴大段日志。

- 正例：「修复 docs-lint 对示例文本误报，改为要求前缀后至少 16 位字符；本地复跑通过。」
- 反例：评论里粘贴两百行构建日志，读者找不到结论。

## 常见反模式

| 反模式 | 正确做法 |
|--------|----------|
| 没看调用点就改函数签名 | 先检索全部调用点再改 |
| 引入新库解决小问题 | 先用仓库已有工具或标准库 |
| 测试红了就跳过用例 | 修根因，或明确标注阻塞 |
| 一次提交混杂多件事 | 一项一提交 |
| 「应该能跑」 | 真的跑一遍并贴结果 |
